# Writing style guidelines



Voice and structure are governed by this document. **Punctuation, casing, terminology, and layout choices follow its rules; formatting on the page is generated by `scripts/generate_report.py`, not invented by the writer — use the helpers (`add_heading`, `add_paragraph`, `add_numbered_list`, `add_table`, `add_glossary_table`, `add_table_caption`, `add_figure_caption`, `add_page_break`) and let the script produce the rendered document.**

## 1. Language

All documentation is written in English. Russian-language narrative is not in scope. Established English technical terms (Wi-Fi, MQTT, RTOS, QoS, EEPROM, CPU, PCB) appear in their canonical form, never translated, never transliterated.

## 2. Software-identifier abstraction

Prose names functional roles, never concrete software identifiers.

| Never in prose | Use instead |
|---|---|
| `AppThread`, `app_thread_entry`, `MQTT_CLIENT_T`, class names | "the application thread", "the MQTT callback" |
| `MX_WIFI_Init()`, `WIFI_Connect()`, function names | "the Wi-Fi manager", "the connection routine" |
| `STATE_INIT`, `state_connected`, enum tags | "the initial state", "the connected state" |
| `LOG_ERR`, `log_error()`, macro names | "the error-log facility", "logging" |
| `mqtt_client_t *client`, struct field names | "the MQTT client", "the client context" |
| Filenames, paths, source-file names | "the firmware", "the configuration module" |

Naming **is** allowed for hardware modules (`MXCHIP Wi-Fi module`, `M2448 non-volatile memory stage`), standards, product names, and standard clause numbers.

**Rationale.** Readers care about hardware (procurement, EMC qualification, swap-out). Software identifiers are implementation details that change between revisions and are not portable across codebases.

## 3. Casing of protocols and standards

Use the casing the owning standards body publishes.

| Correct form | Standard / source |
|---|---|
| Wi-Fi | Wi-Fi Alliance |
| MQTT | OASIS MQTT standard |
| QoS 1 | OASIS MQTT (space between acronym and level) |
| RTOS | Generic; gloss on first use: "Real-Time Operating System (RTOS)" |
| EEPROM | Generic acronym |
| PCB, CPU, API, SoC | Generic acronyms |

Acronyms: spell out with parenthetical gloss on first use, then the acronym only. No second gloss within the same document.

## 4. Tense, voice, hedging

**Tense.**
- Present tense for design description: "the application thread establishes…", "the MQTT callback notifies…".
- Past tense for verification reports: "the device was initialized with…", "the Wi-Fi link was disconnected by…".
- Present tense for verdict and conclusion regardless of genre: "Test result: FAIL."

**Voice.**
- Active voice is the default: "the controller asserts nRESET", "the module attempts to reconnect".
- Passive is acceptable when the agent is genuinely unknown or irrelevant: "the firmware was updated", "the device was placed in the chamber".
- Inanimate subjects must not perform human verbs. No "the Wi-Fi decides", "the state machine believes". Use "the Wi-Fi manager", "the application thread".

**Hedging in formal register.**

| Word | Meaning | Example |
|---|---|---|
| `shall` | mandatory requirement | "the device shall publish within 5 s" |
| `must` | contract-level requirement (use sparingly) | "credentials must be provisioned before deployment" |
| `should` | recommendation | "the handler should be idempotent" |
| `may` | optional / permitted | "the application may retry up to three times" |
| `is expected to` | design intent, not contract | "the manager is expected to back off exponentially" |
| `ensures` | proven / verifiable behavior | "the CRC ensures one-bit-error detection" |

Do not use `just`, `literally`, `honestly`, `actually`, `simply`, `fundamentally`, `essentially`, `basically` in formal docs. They carry no engineering meaning.

## 5. Punctuation

- **The long dash (`—`, em dash) is never used for punctuation.** Compose thoughts with commas, semicolons, colons, or by splitting into two sentences. If an aside is disambiguated by surrounding punctuation, write it as a parenthetical clause or move it into a new sentence.
- Quotation marks only around direct quotations from external sources; never for emphasis.
- Hyphen (`-`) for compound modifiers ("five-volt rail", "state-machine flow"); en dash (`–`) for ranges ("5 V – 12 V", "24 °C – 28 °C"); em dash (`—`) is prohibited.

## 6. Numbers, units, tolerances

- SI units separated from the value with a non-breaking space: `5 V`, `100 ms`, `−40 °C`, `4 kB`.
- Tolerances: choose one form per document and use it throughout.
  - Inline: `5.0 V ± 0.1 V`.
  - Range: `5.0 V (4.9 V to 5.1 V)`.
- Always include units, even when obvious from surrounding context.
- Express quantities in SI multiples: `4.7 kΩ`, `2.4 GHz`, `12 MHz`. Avoid `4 700 Ω` or `2 400 000 000 Hz` in prose.

## 7. Standards references and clause numbers

- Inline cross-references in parentheses: `(see 4.2)`, `(per GOST R IEC 61000-4-2)`.
- Full reference list at the end of the document, with edition and date.
- Self-authored subsection numbers use the trailing-dot convention: `5.`, `5.1.`, `5.1.2.`.

## 8. Paragraph roles

Read the role before drafting. The rhythm and hedge follow it.

| Role | Marker | Rhythm | Hedge |
|---|---|---|---|
| Descriptive (what it is) | "the X is…", "the X shall…" | short, declarative | none / `shall` |
| Rationale (why) | "the choice was driven by…", "this avoids…" | long, coordinate clauses | `is expected to`, `prevents` |
| Methodology (test setup) | "the device was…", "the input was…" | past tense, enumerative | none |
| Reporting (what happened) | "the Wi-Fi was…", "connection was re-established…" | past tense, factual | none |
| Analytical (what it means) | "the deviation indicates…", "this confirms…" | present tense, inferential | `suggests`, `is consistent with` |

Do not collapse two roles into one paragraph.

## 9. Format selection (soft heuristic)

The following table is a starting point; pick the shape that best fits the data and the reader's scanning pattern. Do not treat it as a binding rule.

| When | Format | Example |
|---|---|---|
| Ordered, state-bearing sequence (3+ items) | numbered list | state-machine flow, procedure steps |
| Unordered enumeration (3+ items) | bulleted list | constraints, environmental requirements |
| Structured payload (error data, parameter table) | table | test payload, parameter ranges |
| Causal chain or analysis | prose with conjunctions | rationale paragraphs |

Items: three or more qualifies as a list. One or two items fold into prose.

**State-machine descriptions do not have to be numbered lists.** Numbered lists, prose paragraphs, or prose with inline dash sequences are all acceptable depending on how the document uses the model elsewhere. Keep the format consistent within a single document.

## 10. Patterns to avoid

These appear in generic AI output and read as AI. They do not match a formal technical register.

- Throat-clearing openers: "This document describes…", "The purpose of this section is to…". Open with the subject.
- Importance puffery: "plays a vital role", "marks a pivotal moment". State the fact.
- Faux-insight setups: "What most engineers get wrong…". Make the claim stand on its own.
- Fake-profound kickers: a final aphoristic or metaphorical sentence. End on the last concrete fact or the verdict.
- Summary-recap endings: "In conclusion, …", "Overall, …". Close on the next concrete step (re-test, replaced module, escalated to the hardware team).
- Weasel attribution: "experts agree", "industry reports suggest", "studies show". Name the source or strike the claim.
- Synonym cycling: rotating synonyms for `state`, `manager`, `module`, `callback`. Repeat the clear functional name.
- Mid-sentence bold for emphasis. Reserve bold for table column headers, verdict labels, and field labels.
- Emoji, decorative horizontal rules, headers over two-sentence sections.

## 11. Few-shot examples

### State-machine description (design description)

**Acceptable (state-machine as a list):**

> The application thread drives the following state machine:
>
> 1. Initial state — the Wi-Fi module is initialized.
> 2. Disconnected state — the application establishes a Wi-Fi connection with statically provided credentials. Upon connection, an RTOS primitive signals the MQTT thread.
> 3. Connected state — a subscription request is sent to the MQTT request topic at QoS 1. The subscription verdict is awaited asynchronously. When the subscription verdict arrives, the callback signals the application thread via an RTOS primitive.
> 4. Operational state — the application awaits MQTT publishes. When a publish arrives, the callback signals the application thread. The application reads all reading entries from the EEPROM sequentially and publishes them to the response topic one by one.
> 5. Error state — the application has received an error message. Inside this state the application looks up the error-handling policy and executes the appropriate handler based on the information in the error message.

**Acceptable (state-machine as prose with inline markers):**

> The application thread progresses through five states: initial, disconnected, connected, operational, and error. In the initial state the Wi-Fi module is initialized. In the disconnected state the application establishes the Wi-Fi connection with statically provided credentials and signals the MQTT thread via an RTOS primitive when the link is up. In the connected state a subscription request is sent to the MQTT request topic at QoS 1 and the subscription verdict is awaited asynchronously; once the verdict arrives the MQTT callback signals the application thread via an RTOS primitive. In the operational state the application awaits MQTT publishes; on each publish the callback signals the application thread, which reads all reading entries from the EEPROM sequentially and publishes them one by one to the response topic. The error state is entered when an error message is received; the application looks up the error-handling policy and executes the appropriate handler.

### Error message structure

**Acceptable (table):**

> An error message contains the following fields:

| Field | Description |
|---|---|
| Event ID | The event that caused the error. |
| Previous state | The state where the error occurred. |
| Error code | The exact error code returned. |

**Also acceptable (prose):**

> An error message carries an event ID identifying the event that caused the error, the previous state in which the error occurred, and the exact error code returned by the underlying call.

The format depends on the document's use of tables elsewhere and is not a hard rule.

### Wrong (do not produce)

> *This section describes the application thread state machine. It is very important because state machines are crucial in embedded development. As you can see, the design is robust and showcases the team's commitment to quality. In conclusion, the state machine is a vital part of the system.*
